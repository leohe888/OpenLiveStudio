# 架构与阅读路线

## 先建立一条数据流

```text
用户操作 → MainWindow → 来源管理器 / 来源控制器
视频设备 / 图片 → RenderSourceSnapshot 快照 → VideoSourceAggregator
    → PreviewWidget → Compositor / CanvasRenderer → 预览
                                             → 视频输出订阅 ┐
音频设备 → AudioCaptureWorker → AudioMixer → 音频输出订阅 ───┤
                                                          ↓
                                     OutputTimeline → MediaEncoder
                                                          ↓
                                                 MP4 / RTMP
```

这里有两类数据：来源名称、可见性、变换等是控制状态；视频帧、音频采样是媒体数据。管理器负责状态，控制器负责设备生命周期，工作线程负责持续处理媒体。不要把“来源列表发生变化”和“设备产生了一帧”理解为同一种事件。

## 推荐阅读顺序

1. 从 `src/ui/mainwindow.cpp` 的构造函数开始：来源初始化、预览、输出控制器、错误提示、面板。这里负责组装各模块。
2. 看 `src/video/videosource.h` 和 `videosourcemanager.h`：理解来源的状态和允许的操作。再看图片控制器，沿“添加图片”走到 `VideoSourceAggregator::publishRenderSources()`。
3. 看 `src/graphics/rendersourcesnapshot.h`、`src/ui/previewwidget.cpp` 和 `src/graphics/compositor.h`：快照怎样进入合成器，预览怎样消费合成结果。最后再深入 `CanvasRenderer` 的 GL 实现。
4. 看 `src/audio/audiobuffer.h` 和 `audiomixer.h`：区分采样帧和单声道采样值。当前音频格式为 48 kHz、双声道交错 float。
5. 看 `src/output/outputtimeline.cpp`：`read()` 先收集媒体、检查生产者，再按目标时间选图像，拼出该视频帧对应的音频区间。当前输出节奏为 30 fps，因此每个视频帧对应 1600 个音频帧、3200 个 float。
6. 看 `recordingcontroller.cpp` 与 `streamingcontroller.cpp`：它们各自拥有时间线与编码器，负责停止、错误和恢复策略。最后读 `mediaencoder.cpp` 的 FFmpeg 细节。

## 哪些复杂性有必要保留

- **来源聚合**：将各控制器的媒体快照与来源管理器的可见性、变换和层级合并，渲染端无需分别查询所有控制器。
- **独立输出订阅**：录制与直播不能争抢同一个消费队列。`OutputBus` 发布到各自的有界 `OutputTap`；一个输出停止后，另一个仍可继续消费。
- **统一单调时钟**：音视频对齐依靠媒体时间戳，不能使用会被系统校时改变的墙上时间。
- **缓冲与故障策略**：视频可复用上一帧，缺失音频补静音；音频队列溢出会报错。直播恢复时可丢弃旧历史，录制还需要保证文件封装和连续性。
- **GPU 资源生命周期**：纹理租约、跨 API 同步和工作线程清理涉及实际资源约束，不能因为看起来繁琐就删除。
- **销毁顺序**：主窗口先停止输出，再释放合成器与混音器；面板必须早于其引用的管理器销毁。这也是部分 QObject 延后设置 parent 的原因。

## 如何判断能不能删

`Compositor` 中标记 legacy 的输出接口仍有诊断和测试用途。“旧”不等于“无用”，删除前应查生产代码和测试调用，明确替代路径。本次保留这些接口，也保留设备错误处理、测试延迟注入与平台回退。

后续优先沿一个功能闭环整理：读调用者和测试 → 明确输入输出及所属线程 → 改命名或抽取职责 → 运行对应测试。只有在确认没有调用者、替代方案已覆盖行为后，才删除接口或模块。

## 面试时应该能回答的问题

- 添加一个图片来源，哪些对象依次参与？状态和图像分别由谁持有？
- 为什么预览、录制和直播不能随意共享同一个消费队列？
- 视频帧率不稳定时，时间线如何输出固定节奏？音频空缺如何处理？
- 为什么停止按钮按下后不能立即销毁编码器和合成器？
- 直播积压与录制积压为什么需要不同的处理策略？

回答时结合上述实现与对应测试说明边界，不把尚未验证的硬件编码、设备兼容性或长时间稳定性当成已有保证。

## 摄像头采集与 YUV 渲染

Windows 摄像头使用 Media Foundation 枚举设备、查询原生模式并异步采集。`CameraCaptureWorker` 内部禁用 Source Reader 的格式转换器，输出设备原生数据；设备标识采用 MF symbolic link。设备列表以 MF 能枚举的设备为准，DirectShow 专用虚拟摄像头不保证可见。添加界面按设备、格式、分辨率与帧率联动；每个源的配置只保存在内存中，格式为空表示自动。手动格式或模式协商失败时报告错误，不静默改用其他采集格式。

未压缩输入直接绕过 FFmpeg 解码器；MF 的 2D 缓冲和普通内存缓冲按实际步长与内存边界读取，YV12 的 V/U 顺序整理为 Y/U/V。未压缩输入及软件解码帧保持 YUV 原布局，通过 `CaptureFrame::pixels` 传给 OpenGL。`CanvasRenderer` 复用各源的平面纹理，在 GPU 中转换为合成所需的 RGB。支持 NV12、YUY2、UYVY、8 位平面 YUV 420/422/444 及常见 RGB；MJPEG 和 H.264 交给 `libavcodec` 解码。HDR、10 位和未支持的色彩矩阵会明确报错。

MJPEG/H.264 的 MF 样本转为带 FFmpeg 尾部填充的 `AVPacket`，保留时间戳、可用的解码时间戳、样本时长和关键帧信息；H.264 的 SPS/PPS 从 MF 媒体类型传给解码器。每次只提交一个异步读取请求，由解码线程消费后再读取下一样本，避免应用侧覆盖有依赖的压缩数据；只在完整解码后保留最新画面。压缩输入优先尝试 D3D11VA。硬解帧在 D3D11 视频处理器上完成颜色转换，再通过现有 GPU 互通接入 OpenGL；这条路径不保证零复制。硬解初始化、运行或纹理互通失败时，代码释放硬解上下文并创建软件解码器，只回退一次，摄像头的采集格式不变。H.264 回退后等待关键帧，超时则报错。源列表的提示信息显示实际采集格式、解码方式、回退原因和是否使用了推定色彩信息。

色彩转换优先使用有效元数据；缺失时推定标清 BT.601、高清 BT.709，普通 YUV 有限范围，JPEG 使用解码器提供的全范围语义。预览只保留最新的完整解码帧；GPU 输出纹理池有上限，不通过随意丢弃有依赖的压缩包来降低延迟。设备断开时停止并报错，不自动重连。录制与推流仍沿用合成结果读回 CPU 后编码的既有路径。

验证方式：

- `capture.camera`：配置与格式身份、MF 样本的行填充、负步长、YV12 平面顺序和边界检查，以及压缩样本的时间戳、关键帧和 H.264 初始化数据、生命周期。
- `gpu.compositor`：真实 OpenGL 上的 YUV 颜色、范围、方向及打包像素选择。
- `ui.mainwindow`：格式过滤、模式失效重置、未知格式不可选。
- 设置 `OPENLIVE_CAMERA_HARDWARE=1` 后运行摄像头和界面测试，打开真实设备验证模式、启停和 GPU 预览；设置 `OPENLIVE_CAMERA_FORCE_SOFTWARE=1` 可强制验证软解路径。

硬解覆盖取决于摄像头是否提供对应压缩格式及显卡/驱动能力；不能以软解摄像头测试通过替代硬解验证。性能对比必须使用同设备、同采集模式和同样的预览/输出负载，不预先承诺固定提升比例。

2026-11-04 切换 MF 后，Debug 构建及摄像头、GPU 合成、来源模型、主窗口和录制五组回归通过；真实 GPU 预览、滤镜与编辑测试通过。本机 PC Camera 原生模式查询返回 97 项；MJPEG、NV12、YUY2 采集、显式模式选择、错误模式恢复和隐藏/显示启停通过。2 秒稳定性采样最大画面发布间隔为 66 ms，采样前后私有内存约增加 8 KiB、句柄增加 2；尚未进行长时间稳定性测试。设备列表中未出现此前 DirectShow 能枚举的 OBS Virtual Camera，因此没有声明该虚拟摄像头兼容。

H.264 样本桥接测试使用合成的 MF 样本验证时间戳、IDR 标记和 SPS/PPS 传递，不等同于真实 H.264 摄像头及 D3D11VA 硬解的端到端验证。本机物理摄像头不提供 H.264，该硬件路径仍待对应设备验证。
