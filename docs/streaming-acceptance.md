## 本机结果（2026-10-29）

Windows、Intel Core i5-12600KF、Qt 6.12.0 / MSVC Debug、FFmpeg 9.0.2；Ubuntu 虚拟机运行既有 SRS 6.0.193。使用真实后台 OpenGL 合成、48 kHz 混音、两组独立 H.264/AAC 编码器，同时写 MP4 和推送 RTMP。输入为同钟闪光、1500 Hz 音频脉冲及画面内单调时钟标记。

最终完整运行 1800 秒，`srsEndurance` 通过。独立 ffprobe 和 FFmpeg 再检查全部录制帧，以及直播首尾各 20 秒的 HTTP-FLV 样本。

接收端采用独立 FFmpeg HTTP-FLV 低缓冲解码器，画面时钟精度为 100 ms。延迟包含编码、SRS、传输和解码，不包含物理显示器扫描输出，也不代表任意播放器的默认缓冲。同步工具按实际视频包 PTS 和音频时间线分析，支持直播跳帧后的时间间隙。

本轮长测使用合成校准信号，验证输出链路的稳定性与同步；真实屏幕、摄像头和声音设备的既有验证见[录制综合验收](recording-acceptance.md)。

## 故障与界面验证

- 全部 **11 个 CTest 目标通过**，包括录制、推流、混音、GPU 合成、来源模型、预览和主窗口。
- SRS 集成验证两种启动顺序、独立停止和重启、文件创建失败不影响直播、同名流被断开后的可取消重试，以及持续编码过载后停止直播。
- 注入 **1.2 秒直播编码暂停**：原连接继续，过期画面被跳过，发送前验证新关键帧标志；接收端音视频 DTS 单调，恢复文件实际解码成功，录制继续。SRS 的默认 full 时间戳校正会压缩较大时间跳变，因此不以接收端是否保留原始间隙判定恢复。
- TCP 中继验证连接中断、拒绝连接、恢复和背压；重连期间本地录制连续。另实际重启 SRS 容器，推流自动恢复，60 秒本地文件连续、无缺失混音采样。
- 单次 **550 ms 录制调度暂停**能够补算恢复，不误触发停播；持续编码过载仍报错并完成已有 MP4 内容。单次 **80 ms 混音暂停**补算后输出时间戳连续。
- 原生窗口验证密钥遮蔽、草稿取消、深浅主题、两路配置分别锁定、重连期间可停止，以及关闭窗口等待两路释放资源；全部通过。

长测曾暴露两类需要处理的行为：瞬时调度积压不应等同于持续编码过载；混音晚到超过 40 ms 就跳过时间段会留下静音缺口。当前实现通过直播跳帧并强制关键帧、观察持续编码速度、录制优先调度、音频线程优先调度，以及最多 100 ms 混音补算解决；最终结果使用这些修正后的代码重新完整运行。
