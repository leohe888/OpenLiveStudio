# OpenLive Studio 实施路线

本路线记录实施顺序、阶段目标和验收边界；MVP 功能范围见[项目方案](openlive-studio-plan.md)，协作与审核规则见[AGENTS.md](../AGENTS.md)。

先完成“单摄像头 → 预览 → 本地录制”，再逐步扩展到多来源、音频、多场景和推流。以下各阶段均为计划，不代表已经实现。

## 当前基线

截至 2026-10-26：

- 已有场景和来源管理的部分数据与界面。
- FFmpeg 已接入 CMake，使用 libavdevice 作为采集入口；Windows MSVC 构建、实际库调用及 DLL 加载已验证，现有测试通过。
- 摄像头采集、真实预览、画面合成、编码录制和推流尚未实现。
- 来源共享、采集线程与缓冲、自定义预览组件均处于设计讨论阶段。
- Linux、真实采集设备及采集图形集成尚未验证；现有 CI 尚未配置 FFmpeg 依赖。

## 技术与实施边界

- 保留 Qt 6 Widgets + QML 混合架构：Widgets 管理主窗口、停靠容器和原生窗口，中央预览采用 QOpenGLWidget；QML 继续负责面板、参数展示与交互；C++ 统一管理业务状态和音视频处理。
- 界面通过 C++ 属性、信号和方法传递状态与操作，不直接持有 FFmpeg 采集、编码上下文。
- OpenGL 渲染逻辑与 QOpenGLWidget 分离：渲染模块负责纹理、画面变换和后续场景合成，预览控件负责显示与鼠标交互，交互结果交由 C++ 更新业务状态。
- 采集线程只交付视频帧，不直接操作预览控件或其 OpenGL 上下文；初版在预览控件的 paintGL() 中绘制，采用 QOpenGLWidget 不代表已经具备独立渲染线程。线程调度、通知合并和图形资源释放随对应步骤确认。
- 初版只运行当前场景的视频来源，同时使用一台摄像头；跨场景来源共享和无缝切换暂缓。
- 每个独立的 libavdevice 输入初步采用自己的采集工作线程，通过有界缓冲交付数据；具体停止机制、帧所有权和时间戳规则随采集步骤验证。
- 视频初版采用 CPU 内存帧，音频初版采用全局输入。GPU 零拷贝、硬件编码和转场动画暂缓。
- 模块目录随实际功能增加，不提前创建完整框架或空的平台实现。Linux 扩展集中适配平台采集、授权、图形资源和构建部署。
- 每个阶段拆成小步骤，实施前只读检查并确认方案，完成一步后等待审核。下表不代替具体步骤的文件范围、测试和授权。

## 阶段路线

| 阶段 | 目标与范围 | 阶段验收 |
|---|---|---|
| 1. 摄像头采集 | 依次完成设备枚举、设备选择、采集与必要解码、启停和错误处理；暂不修改预览 | 能列出真实摄像头名称和 ID；打开指定设备并收到真实帧；停止后释放设备，能够再次启动；区分无设备与采集失败 |
| 2. 单摄像头预览 | 在 Widgets 中央容器中使用 QOpenGLWidget 显示采集帧，通过纹理与着色器绘制；Qt OpenGLWidgets 依赖、帧交付、上下文生命周期及资源释放需在实施方案中确认 | 主窗口显示真实画面，比例与颜色正确；窗口尺寸变化正常；未启动、等待首帧和错误状态明确； |
| 3. 单路视频录制 | 将单摄像头帧送入软件编码与封装，先输出无音频 MKV；录制开始、停止及失败状态来自真实结果 | 停止后文件可播放，尺寸、时长和帧率合理；录制启停不破坏采集生命周期；写入失败明确报告 |
| 4. 单场景多来源合成 | 逐个加入显示器、窗口、图片和文字；按固定场景尺寸合成，支持位置、缩放、层级和可见性；将编码输入接到合成结果 | 预览与录制内容一致；调整预览窗口不改变输出分辨率；来源变化与释放正确；静态来源无需持续采集线程 |
| 5. 音频接入 | 先麦克风，再系统音频；完成重采样、声道转换、音量、静音、混音和音画同步 | 两种声音能够独立控制并录入文件；同步偏差可测量；长时间运行不持续积压数据，设备异常能够报告 |
| 6. 多场景运行与保存 | 保存与恢复场景、来源配置；仅支持直接切换，管理旧场景停止与新场景启动；暂不实现共享来源和转场 | 重启后配置可恢复；切换时录制持续，输出时间线连续；短暂黑屏、等待首帧及音频保持策略明确并验证 |
| 7. RTMP 推流 | 复用场景合成与音频处理链路，接入编码、连接、发送、停止和断线处理 | 接收端可播放；连接失败与断线状态准确；按确认的策略重连；录制与推流的启停关系明确并验证 |
| 8. Linux 扩展 | 先选定发行版与桌面环境，再逐项适配采集、权限、图形和打包；X11 与 Wayland 分别确认支持范围，Wayland 屏幕共享需专门适配 | 在明确的目标环境验证摄像头、屏幕/窗口、音频、预览和输出；兼容范围及未支持能力有实际记录 |

第 3 阶段先验证单路编码与文件输出；第 4 阶段复用编码和封装模块，将其输入调整为合成画面。预览与编码最终消费同一场景合成链路，预览尺寸不决定输出尺寸。合成按固定输出尺寸生成画面，编码不依赖预览窗口截图或逐帧调用 grabFramebuffer()；离屏合成、输出调度及帧传递方式在合成阶段单独确认。

MVP 中的 MP4、快捷键、硬件编码及文件修复等能力，分别在录制、输出控制或异常恢复对应阶段另行确认小步骤，不在当前摄像头步骤中提前实现，也不因本路线未展开而视为已完成。

## 当前下一步

先实现摄像头设备枚举：取得真实设备名称和 ID，过滤音频设备，区分无设备和枚举失败，正确释放资源。

设备枚举审核通过后，再提出采集启停方案；收到并验证真实帧后，才进入预览阶段。当前不实施多来源共享、合成、混音或 Linux 后端。

## 验证与交付

- 自动测试优先使用可控素材，验证数据处理、边界、错误和资源生命周期；设备枚举、真实采集与图形显示单独记录。
- 每步运行适合本次改动的构建和测试，不把离屏 Widgets 测试通过当作 QML、GPU 或真实设备验证通过。
- 录制、同步与性能结果说明测试环境和测量方法；未具备设备或平台条件时标记“未验证”。
- 完成后提供改动文件、行为说明、实际验证结果、手工验收方法、重点审核位置及已知限制；不自动进入下一步或提交。
